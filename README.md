# MaxPatrol VM → Jira

Интеграция получает активы и актуальные уязвимости из MaxPatrol VM, сохраняет датированный JSON-снимок и создает в Jira по одной задаче на каждый уязвимый актив.

Поддерживаются:

- MaxPatrol VM 2.10 с персональным reference-токеном `pat_…`;
- Jira REST API;
- оформленное XLSX-вложение с уязвимостями для каждого актива;
- фильтрация XLSX и таблицы Jira по выбранным уровням критичности;
- отдельные команды `validate`, `export`, `sync`, `run`, `latest`;
- dry-run, журналы и защита от повторной обработки одного JSON.

## 0. Быстрый старт

> ❗ **Обязательно:** конфиденциальная информация должна храниться только в локальном файле `.env`. По умолчанию этот файл отсутствует. Не добавляйте `.env` в Git.

1. Клонируйте репозиторий, создайте виртуальное окружение и локальные файлы настроек:

   ```bash
   git clone https://github.com/OlegKocha/mpvm-jira-integration.git && cd mpvm-jira-integration && python3 -m venv .venv && source .venv/bin/activate && python -m pip install -r requirements.txt && cp .env.example .env && cp config.example.yaml config.yaml && chmod 600 .env config.yaml
   ```

2. Выпустите reference-токен MP VM и запишите его в `.env` как `MPVM_ACCESS_TOKEN`. Подробнее — в разделе [«Получение токена MaxPatrol VM»](#2-получение-токена-maxpatrol-vm).
3. Выпустите API-токен Jira и запишите в `.env` значения `JIRA_USER` и `JIRA_API_TOKEN`. Подробнее — в разделе [«Получение учетных данных Jira»](#3-получение-учетных-данных-jira).
4. Отредактируйте локальный файл `config.yaml`: укажите адрес Jira в `jira.base_url` и замените `SEC` в `jira.project_key` на ключ проекта, в котором скрипт должен создавать задачи.

По желанию файлы `config.example.yaml` и `.env.example` можно удалить после их конфигурации.

5. Проверьте конфигурацию, токены и подключения к MP VM и Jira:

   ```bash
   python -m mpvm_jira --config config.yaml --env-file .env validate
   ```

6. Запустите полный цикл:

   ```bash
   python -m mpvm_jira --config config.yaml --env-file .env run
   ```

## 1. Что понадобится

- Python 3.10 или новее;
- сетевая доступность HTTPS от узла запуска до MP VM и Jira;
- техническая учетная запись MP VM с правом чтения активов/уязвимостей и выполнения PDQL;
- учетная запись Jira с правами `Browse projects`, `Create issues` и `Create attachments` в целевом проекте;
- доверенный корневой сертификат внутреннего УЦ, если API используют частные сертификаты.

### Перед первым запуском

Подготовьте учетные записи, токены и параметры обеих систем до установки интеграции.

1. **Создайте техническую учетную запись MaxPatrol VM.** Выдайте ей только права чтения активов, уязвимостей, паспортов уязвимостей и выполнения PDQL-запросов.
2. **Получите reference-токен MP VM.** Выпустите PAT от имени технической учетной записи, сохраните его в менеджере секретов и запишите в локальный `.env` как `MPVM_ACCESS_TOKEN`. Подробная инструкция приведена в разделе [«Получение токена MaxPatrol VM»](#2-получение-токена-maxpatrol-vm).
3. **Создайте техническую учетную запись Jira.** Не используйте личную учетную запись администратора для регулярных запусков.
4. **Получите учетные данные Jira.** Создайте API-токен технической учетной записи и запишите логин и токен только в локальный `.env` как `JIRA_USER` и `JIRA_API_TOKEN`.
5. **Настройте права Jira.** Учетной записи нужны как минимум `Browse projects`, `Create issues` и `Create attachments` в целевом проекте. Вложения должны быть включены глобально, расширение `.xlsx` должно быть разрешено, а лимит размера — достаточен для отчета.
6. **Соберите параметры Jira.** Понадобятся URL Jira, ключ проекта, точное имя типа задачи, имена приоритетов и перечень обязательных custom fields на экране создания задачи.
7. **Проверьте сеть и TLS.** Узел запуска должен открывать HTTPS API MP VM и Jira. Для внутренних сертификатов подготовьте PEM-файл корпоративного CA; не используйте `verify_ssl: false` в production.
8. **Установите Python 3.10 или новее** и зависимости проекта.
9. **Создайте локальные конфигурационные файлы из примеров:**

   ```bash
   cp .env.example .env
   cp config.example.yaml config.yaml
   chmod 600 .env
   ```

10. **Замените заглушки только в локальных файлах.** Заполните `.env` реальными токенами, а `config.yaml` — адресами ваших систем и параметрами проекта. Файлы `.env` и `config.yaml` исключены из Git и не должны отправляться в репозиторий, мессенджер, issue или pull request.
11. **Проверьте подключения без создания задач:**

    ```bash
    python -m mpvm_jira --config config.yaml --env-file .env validate
    ```

12. **Выполните тестовый запуск без записи в Jira** с `sync --dry-run` или `run --dry-run`, изучите JSON, план задач и журнал, а затем разрешайте production-запуск.

Перед первым коммитом убедитесь, что в staged-файлах нет `.env`, `config.yaml`, журналов, JSON/XLSX-выгрузок, внутренних сертификатов, реальных FQDN/IP и токенов. Если секрет хотя бы один раз попал в commit или push, простого удаления файла недостаточно: секрет нужно отозвать или заменить и очистить историю репозитория.

## 2. Получение токена MaxPatrol VM

Рекомендуется отдельная техническая учетная запись и минимальная роль.

1. Войдите в MaxPatrol VM под технической учетной записью.
2. Откройте приложение **Positive Technologies Management and Configuration (PT MC)**.
3. В главном меню выберите меню пользователя → **Токены доступа**.
4. Нажмите **Создать**.
5. Укажите понятное имя, например `mpvm-jira-integration`.
6. Укажите срок действия.
7. Выберите приложение MaxPatrol, права которого должен нести токен.
8. Нажмите **Создать**, затем скопируйте значение. Reference-токен имеет префикс `pat_`.

Токен показывается один раз. Сохраните его в менеджере секретов. Привилегии токена фиксируются в момент создания; после изменения ролей создайте новый токен. Документация MP VM также указывает: если API отвечает HTTP 500 из-за прав, назначьте технической учетной записи минимально необходимую роль приложения Management and Configuration и выпустите токен заново.

PDQL-токен отдельно создавать вручную не нужно: скрипт получает короткоживущий (30 минут) PDQL-токен запросом к API на основании Bearer PAT.

## 3. Получение учетных данных Jira

1. Создайте отдельную техническую учетную запись Jira.
2. В профиле этой учетной записи создайте API-токен, задайте срок действия и сразу скопируйте его.
3. Запишите логин технической учетной записи в `.env` как `JIRA_USER`, а токен — как `JIRA_API_TOKEN`.
4. В локальном файле `config.yaml` укажите адрес Jira в `jira.base_url` и замените пример `jira.project_key: "SEC"` на ключ целевого проекта. Нужен короткий ключ, а не полное название проекта: например, для задачи `SEC-123` ключом будет `SEC`.
5. Убедитесь, что учетная запись имеет необходимые права в целевом проекте.

### Обязательная настройка Jira для XLSX-вложений

PAT или API token не выдает дополнительных прав: скрипт выполняет запросы с правами той учетной записи Jira, для которой создан токен. До первого запуска администратор Jira должен разрешить этой учетной записи создание задач и прикрепление файлов в целевом проекте.

Минимальные проектные разрешения технической учетной записи:

- `Browse projects` — видеть проект и созданные задачи;
- `Create issues` — создавать задачи;
- `Create attachments` — прикреплять XLSX к уже созданной задаче.

Разрешения `Delete own attachments` и `Delete all attachments` для работы интеграции не требуются. Их следует выдавать только тогда, когда скрипт должен удалять или заменять старые вложения.

1. В административных настройках Jira откройте раздел **Attachments**.
2. Убедитесь, что вложения включены и максимальный размер одного файла больше ожидаемого размера XLSX.
3. Если в Jira настроен allowlist/blocklist расширений, разрешите расширение `xlsx`.
4. Откройте схему разрешений целевого проекта и перейдите в **Permissions**.
5. В строке **Create attachments** нажмите **Grant permission** и выдайте право группе или проектной роли технической учетной записи.
6. Убедитесь, что техническая учетная запись действительно входит в выбранную группу или роль именно в целевом проекте.

После настройки войдите под технической учетной записью и вручную прикрепите небольшой `.xlsx` к тестовой задаче. Право также можно проверить через REST API:

```text
GET /rest/api/2/mypermissions?projectKey=<PROJECT_KEY>&permissions=CREATE_ATTACHMENTS
```

Ожидаемый результат: `permissions.CREATE_ATTACHMENTS.havePermission` имеет значение `true`. Глобальное состояние и лимит вложений возвращает запрос:

```text
GET /rest/api/2/attachment/meta
```

Если создание задачи проходит, а загрузка XLSX возвращает HTTP 403 с сообщением `You do not have permission to create attachments for this issue`, значит вложения включены, но у учетной записи нет проектного разрешения `Create attachments`. Выдайте разрешение в схеме проекта; перевыпускать PAT после этого обычно не требуется, поскольку Jira проверяет текущие права учетной записи при каждом запросе.

## 4. Установка

Linux/macOS:

```bash
cd /path/to/mpvm-jira-integration
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp config.example.yaml config.yaml
cp .env.example .env
chmod 600 .env
```

Windows PowerShell:

```powershell
cd C:\path\to\mpvm-jira-integration
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
Copy-Item config.example.yaml config.yaml
Copy-Item .env.example .env
```

Пакет можно также установить в venv командой `python -m pip install .`; после этого доступна команда `mpvm-jira`.

### Структура модулей

Код интеграции разделен на два независимых прикладных модуля:

```text
mpvm_jira/
├── mpvm/
│   ├── client.py       # запросы к API MaxPatrol VM и выполнение PDQL
│   ├── service.py      # получение активов и уязвимостей
│   └── snapshot.py     # создание, чтение и поиск JSON-снимков
├── jira/
│   ├── client.py       # запросы к API Jira и формирование описания задачи
│   ├── criticality.py  # фильтрация уязвимостей по критичности
│   ├── service.py      # чтение JSON и создание задач с вложениями
│   └── xlsx_export.py  # формирование XLSX для отдельного актива
├── cli.py              # команды и аргументы командной строки
├── config.py           # загрузка и проверка конфигурации
├── http.py             # общая настройка HTTP-сессий и повторных запросов
└── models.py           # общие модели активов и уязвимостей
```

Команда `export` использует только модуль `mpvm`: получает данные из MaxPatrol VM и сохраняет JSON. Команда `sync` использует модуль `jira`: читает готовый JSON, создает XLSX и задачи Jira. Команда `run` последовательно выполняет оба этапа.

## 5. Настройка

### Секреты `.env`

```dotenv
MPVM_ACCESS_TOKEN=replace_with_mpvm_reference_token
JIRA_USER=jira-service-account@example.org
JIRA_API_TOKEN=replace_with_jira_token
```

Не передавайте `.env` в Git, резервные копии общего доступа или систему заявок.

### Основные параметры `config.yaml`

Скопируйте `config.example.yaml` и измените:

- `mpvm.base_url` — корневой HTTPS URL MP VM, обычно без `/api`;
- `mpvm.verify_ssl` — `true` или путь к PEM-файлу внутреннего CA;
- `mpvm.assets_pdql` — запрос активов, включая `OsName` и `OsVersion`;
- `mpvm.software_vulnerabilities_pdql` — отдельный запрос связей уязвимостей с установленными пакетами;
- `jira.deployment`, `jira.api_version`, `jira.auth_mode` — параметры подключения к API вашей Jira;
- `jira.base_url` — адрес Jira;
- `jira.project_key` — ключ проекта;
- `jira.issue_type` — точное имя типа задачи, например `Task` или `Задача`;
- `jira.priority_map` — точные имена приоритетов вашей Jira;
- `jira.strict_attachment_permissions` — требовать право `Create attachments` при `validate`;
- `jira.attachment_subdir` — имя каталога XLSX рядом с JSON-снимком;
- `jira.max_issues_per_run` — ограничение новых задач за запуск (`0` — без ограничения, для первого теста используйте `1`);
- `jira.additional_fields` — обязательные custom fields проекта.

> ❗ **Обязательно:** замените пример `jira.project_key: "SEC"` на ключ проекта Jira, в котором скрипт должен создавать задачи.

Пример русской карты приоритетов Jira:

```yaml
jira:
  default_priority: "Средний"
  priority_map:
    High: "Высокий"
    Medium: "Средний"
    Low: "Низкий"
    Undefined: "Средний"
```

Если экран создания требует пользовательское поле:

```yaml
jira:
  additional_fields:
    customfield_12345:
      value: "Information Security"
```

### Внутренний удостоверяющий центр

Не отключайте TLS-проверку в production. Сохраните цепочку CA в доступном процессу файле:

```yaml
mpvm:
  verify_ssl: "/etc/pki/ca-trust/source/anchors/company-ca.pem"
jira:
  verify_ssl: "/etc/pki/ca-trust/source/anchors/company-ca.pem"
```

### Проверка PDQL

Запросы по умолчанию соответствуют псевдонимам MP VM 2.10. Перед production:

1. выполните эквивалентный запрос в таблице активов MP VM;
2. убедитесь, что возвращаются `AssetId`, FQDN, IP, значимость, `OsName`, `OsVersion` и нужные поля уязвимости;
3. проверьте, что `software_vulnerabilities_pdql` возвращает `AssetId`, `VulnerabilityId`, `PackageName`, `PackageVersion` и `Status`;
4. при необходимости замените `assets_pdql`, `vulnerabilities_pdql` и `software_vulnerabilities_pdql` в YAML;
5. если нужны только уязвимости текущего узла, замените `@Vulners` на подходящие псевдонимы `@NodeVulners`;
6. согласуйте набор `active_statuses`.

Запрос связей с пакетами вынесен отдельно намеренно. Добавление `Host.Softs.Name` и `Host.Softs.Version` непосредственно в общий `vulnerabilities_pdql` может перемножить все уязвимости актива на всё установленное ПО и сформировать недостоверный XLSX.

По умолчанию включены `new`, `inProgress`, `awaitingFix`, `overdue`, `stale`; `fixed` и `excluded` не выгружаются.

## 6. Проверка подключений

```bash
python -m mpvm_jira --config config.yaml --env-file .env validate
```

Команда проверяет Bearer-токен MP VM, Jira user, справочник приоритетов и разрешения `Create issues`/`Create attachments`. Она не создает задач.

Типовые причины ошибки:

- HTTP 401 — неверный или истекший токен либо неверный логин Jira;
- HTTP 403 — нет прав на API/проект;
- HTTP 500 MP VM — у PAT недостаточно прав, после изменения роли нужен новый PAT;
- TLS error — процесс не доверяет внутреннему CA;
- приоритет не найден — значения `priority_map` не совпадают с именами Jira.

## 7. Запуск

Все снимки и state-файл создаются относительно `--base-dir`. При использовании `--debug` там же создается каталог `logs`. Если `--base-dir` не указан, используется текущая директория запуска.

### Доступные команды и флаги

`validate`, `export`, `sync`, `run` и `latest` — это команды. Параметры, начинающиеся с `--`, являются флагами.

Команды:

| Команда | Назначение |
|---|---|
| `validate` | Проверить конфигурацию, токены и подключения к MP VM и Jira без создания задач. |
| `export` | Получить данные из MP VM и сохранить новый JSON-снимок. |
| `sync` | Прочитать последний JSON-снимок и создать задачи Jira с XLSX-вложениями. |
| `run` | Выполнить полный цикл: `export`, затем `sync`. |
| `latest` | Показать путь к последнему сохраненному JSON-снимку. |

Глобальные флаги указываются перед командой:

| Флаг | Назначение |
|---|---|
| `-h`, `--help` | Показать справку. Для справки по конкретной команде используйте, например, `run --help`. |
| `--config PATH` | Указать путь к YAML-конфигурации. По умолчанию используется `config.yaml`. |
| `--env-file PATH` | Указать путь к файлу с секретами. По умолчанию используется `.env`. |
| `--base-dir PATH` | Указать каталог для JSON-снимков, XLSX-вложений, state-файла и журналов. |
| `--verbose` | Включить подробный вывод в терминал без создания файла журнала. |
| `--debug` | Включить подробное логирование в файл `<base-dir>/logs/mpvm_jira_ГГГГММДД.log`. |

Флаги отдельных команд указываются после команды:

| Флаг | Доступен для | Назначение |
|---|---|---|
| `--fqdn FQDN [FQDN ...]` | `export`, `run` | Обработать один или несколько активов по списку FQDN. |
| `--ip IP_OR_RANGE [IP_OR_RANGE ...]` | `export`, `run` | Обработать активы по списку IPv4/IPv6-адресов и диапазонов `НАЧАЛО-КОНЕЦ`. |
| `--dry-run` | `sync`, `run` | Сформировать план обработки без создания задач и вложений в Jira. При `run` новый JSON сохраняется. |
| `--criticality LEVEL [LEVEL ...]` | `sync`, `run` | Передать в XLSX и сводную таблицу Jira только выбранные уровни: `Critical`, `High`, `Medium`, `Low`, `Non-crit`. |

Примеры массового выбора активов.

Несколько FQDN:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira run --fqdn srv01.example.org srv02.example.org srv03.example.org
```

Несколько IP-адресов:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira run --ip 192.0.2.10 192.0.2.11 192.0.2.12
```

Диапазон IP-адресов, включая обе границы:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira run --ip 192.0.2.10-192.0.2.15
```

Один запуск формирует общий JSON, а затем создает отдельную задачу Jira и XLSX-вложение для каждого найденного уязвимого актива. Флаги `--fqdn` и `--ip` взаимоисключающие. Глобальные флаги необходимо ставить перед командой, а флаги конкретной команды — после неё.

### Только выгрузить MP VM в JSON (`export`)

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira export
```

Пример результата:

```text
/var/lib/mpvm-jira/05.08.2026/vulnerabilities_14.32.08.json
```

### Показать последний снимок (`latest`)

```bash
python -m mpvm_jira --base-dir /var/lib/mpvm-jira latest
```

### Проверить задачи без записи в Jira (`sync --dry-run`)

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira sync --dry-run
```

### Создать задачи из последнего JSON (`sync`)

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira sync
```

### Полный цикл (`run`)

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira run
```

### Обработать активы и создать задачи (`run --fqdn` / `run --ip`)

Чтобы получить из MP VM актуальные уязвимости выбранных активов, сохранить общий JSON и создать по одной задаче Jira с XLSX-вложением для каждого уязвимого актива, перечислите FQDN, IP-адреса или диапазоны после команды `run`. Варианты запуска приведены в начале этой главы, в разделе «Доступные команды и флаги».

### Выгрузить активы без обращения к Jira (`export --fqdn` / `export --ip`)

Эти же массовые фильтры доступны команде `export`, если требуется только сформировать общий JSON без обращения к Jira:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira export --fqdn srv01.example.org srv02.example.org srv03.example.org
```

Пример со списком IP и диапазоном:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira export --ip 192.0.2.10 192.0.2.20-192.0.2.30
```

Флаги `--fqdn` и `--ip` взаимоисключающие, но каждый из них принимает сколько угодно значений в пределах максимальной длины команды операционной системы. Повторяющиеся значения автоматически удаляются. Диапазон должен содержать адреса одной версии IP, а его начало не может быть больше конца.

Скрипт добавляет групповой фильтр во все PDQL-запросы. Список IP передается через оператор PDQL `intersect`, а диапазон преобразуется в минимальный набор CIDR-подсетей, поэтому каждый адрес диапазона отдельно в запрос не записывается. Если ни один актив не найден, создается пустой JSON и задачи Jira не создаются. Активы без актуальных уязвимостей остаются в JSON без списка уязвимостей, но задачи для них не создаются.

При массовом запуске проверьте `jira.max_issues_per_run`: значение `0` разрешает создать задачи для всех найденных уязвимых активов, а положительное значение ограничивает число новых задач за один запуск.

### Фильтрация уязвимостей по критичности (`run --criticality` / `sync --criticality`)

Команды `run` и `sync` принимают флаг `--criticality LEVEL [LEVEL ...]`. После него можно перечислить один или несколько уровней:

- `Critical` — критические;
- `High` — высокие;
- `Medium` — средние;
- `Low` — низкие;
- `Non-crit` — без вектора CVSS, даже если в MP VM присутствует числовая оценка.

Только критические уязвимости выбранного актива:

```bash
python -m mpvm_jira --config config.yaml --env-file .env run --fqdn srv01.example.org --criticality Critical
```

Критические и высокие:

```bash
python -m mpvm_jira --config config.yaml --env-file .env run --fqdn srv01.example.org --criticality Critical High
```

Только уязвимости без вектора CVSS:

```bash
python -m mpvm_jira --config config.yaml --env-file .env run --fqdn srv01.example.org --criticality Non-crit
```

Фильтрация уже сохраненного последнего JSON:

```bash
python -m mpvm_jira --config config.yaml --env-file .env sync --criticality Critical High
```

Проверка результата без создания задач Jira:

```bash
python -m mpvm_jira --config config.yaml --env-file .env sync --dry-run --criticality Critical High
```

Регистр и порядок значений не важны, повторения удаляются. Неизвестное значение останавливает запуск с сообщением о допустимых уровнях. Без флага `--criticality` в XLSX и задачу попадают все уровни.

При `run` исходный JSON всегда сохраняется полностью. Фильтр применяется позднее только к XLSX-вложению и сводной таблице Jira. В таблице выводятся только выбранные строки, а `Всего уязвимостей` означает количество после фильтрации. Если подходящих уязвимостей у актива нет, задача Jira и XLSX не создаются.

### Полный цикл без записи в Jira (`run --dry-run`)

Полный цикл с реальной выгрузкой, но без записи в Jira:

```bash
python -m mpvm_jira --config config.yaml --env-file .env --base-dir /var/lib/mpvm-jira run --dry-run
```

## 8. Что создается в Jira

Одна задача на один уязвимый актив. Summary:

- `srv01.example.org (192.0.2.10)`, если есть FQDN и IP;
- `srv01.example.org`, если есть только FQDN;
- `192.0.2.10`, если есть только IP;
- `Актив <UUID>`, если оба поля отсутствуют.

Loopback-адреса (`127.0.0.0/8`, `::1`), link-local-адреса (`169.254.0.0/16`, `fe80::/10`) и неопределенные адреса (`0.0.0.0`, `::`) не выводятся в Summary и описании задачи. Частные адреса инфраструктуры, например `10.0.0.0/8`, сохраняются. В исходном JSON остается полный список адресов, полученный от MP VM.

В описании указываются источник, строка `Актив из MaxPatrol VM` и сводная таблица актуальных уязвимостей без заголовка. Первая строка содержит общее количество, затем идут уровни критичности:

```text
Всего уязвимостей                       125
Критического уровня                     10
Высокого уровня                         35
Среднего уровня                         50
Низкого уровня                          25
Без критичности (без вектора CVSS)       5
```

В Jira строка `Всего уязвимостей` и итоговое число выделяются жирным. Уровни критичности имеют фиксированные цвета: критический — алый (`#FF2400`), высокий — красный (`#D32F2F`), средний — приглушенный оранжевый (`#B86E00`), низкий — синий (`#0052CC`). Строка без критичности остается черной.

Категории не пересекаются: уязвимость без вектора CVSS относится в последнюю строку, даже если в MP VM для нее присутствует числовая оценка. Имя JSON-снимка в описание задачи не добавляется.

К задаче прикладывается отдельный XLSX-файл с листом `Уязвимости`:

| № | CVE | BDU | ОС | Пакет | Версия пакета | Описание | How to fix | CVSS vector | Критичность | CVSS score |
|---:|---|---|---|---|---|---|---|---|---|---:|
| 1 | CVE-2026-1234 | BDU:2026-00001 | Debian 12 | openssl | 3.0.11-1 | Описание из MP VM | Рекомендация из MP VM | CVSS:3.1/AV:N/... | Высокий | 8.5 |

ОС формируется из `Host.OsName` и `Host.OsVersion`. Название и версия пакета берутся только из связи `Host.Softs.@Vulners`. Если MP VM не связал уязвимость с конкретным объектом ПО, в полях пакета записывается `-`: скрипт не пытается угадать пакет по тексту описания. Если одной уязвимости соответствуют несколько пакетов, названия и версии перечисляются через `;` в одинаковом порядке в соседних ячейках.

Если CVE, BDU или сведения об ОС отсутствуют, в соответствующей ячейке записывается `-`. Несколько идентификаторов одного типа перечисляются через запятую. Значение CVSS сохраняется как число, чтобы в Excel его можно было сортировать и фильтровать. Строки идут в порядке убывания CVSS.

XLSX открывается в Microsoft Excel без выбора кодировки и разделителя. В первой строке включены заголовки и фильтры, первая строка закреплена, длинные описания и рекомендации переносятся внутри ячеек, а ширина столбцов настроена для чтения.

XLSX создается в `<каталог снимка>/attachments/` и загружается через Jira REST API как `multipart/form-data` с MIME-типом `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` и заголовком `X-Atlassian-Token: no-check`.

## 9. Повторные запуски

Файл `.mpvm-jira-state.json` хранит пары «хеш снимка + asset_id», выбранные уровни критичности, ключи задач и состояние XLSX-вложения. Ключ записывается сразу после создания задачи, до загрузки файла. Поэтому, если загрузка XLSX завершилась ошибкой, повторный `sync` с тем же фильтром прикрепит файл к уже созданной задаче и не создаст дубль. Полностью обработанный идентичный JSON с тем же набором уровней пропускается. Разные наборы `--criticality` обрабатываются независимо и могут создать отдельные задачи из одного снимка.

Новый снимок сейчас считается новым циклом и может создать новую задачу для того же актива.

## 10. Планировщик

Пример cron каждый день в 02:15 (пути должны быть абсолютными):

```cron
TZ=Europe/Moscow
15 2 * * * /opt/mpvm-jira/.venv/bin/python -m mpvm_jira --config /opt/mpvm-jira/config.yaml --env-file /opt/mpvm-jira/.env --base-dir /var/lib/mpvm-jira run >> /var/log/mpvm-jira-cron.log 2>&1
```

Убедитесь, что каталог `/var/lib/mpvm-jira`, `.env` и CA-файл доступны только сервисной учетной записи. Для production предпочтительнее systemd timer или корпоративный scheduler с менеджером секретов.

## 11. Журналы и диагностика

По умолчанию скрипт выводит основные события в терминал, но не создает каталог `logs` и не записывает файловый журнал. Чтобы включить подробный журнал, добавьте глобальный флаг `--debug` до имени команды:

```bash
python -m mpvm_jira --debug --config config.yaml --env-file .env run --fqdn srv01.example.org
```

При первом таком запуске создаются:

- каталог `<base-dir>/logs/` с правами `700`;
- файл `<base-dir>/logs/mpvm_jira_ГГГГММДД.log` с правами `600`.

Запуски за один день дописываются в общий файл. Журнал содержит команду и безопасные параметры запуска, пути к конфигурации и JSON, адреса MP VM и Jira, ключ проекта, FQDN/IP-фильтр, сформированные PDQL-запросы, количество полученных записей, статистику снимка, создание задачи и результат загрузки XLSX. Токены, пароли и содержимое `.env` в журнал не выводятся.

Флаг `--verbose` отвечает только за подробный вывод в терминал и сам по себе файл не создает. Флаги можно использовать одновременно:

```bash
python -m mpvm_jira --debug --verbose --config config.yaml --env-file .env validate
```

Тело ответа API при ошибке не записывается в сообщение исключения. Не помещайте токены в параметры URL или поля данных. Журнал может содержать внутренние URL, пути, FQDN и IP-адреса, поэтому не публикуйте его и не добавляйте в Git.

## 12. Известные ограничения

- Точные поля PDQL нельзя гарантировать без ответа реальной инсталляции MP VM.
- Очень большой XLSX может превысить глобальный лимит вложений Jira; лимит нужно проверить до production-запуска.
- Один общий PDQL-запрос может упереться в лимит строк MP VM; для крупного контура запросы следует делить по группам/активам или временным диапазонам.
- Проверка приоритетов использует глобальный справочник Jira; схема конкретного проекта может быть строже.
- Скрипт не обновляет и не закрывает ранее созданные задачи.
- `sync --dry-run` загружает Jira-конфигурацию и секреты, но не выполняет HTTP-запросов и не создает задач.
- Если два процесса одновременно обрабатывают один снимок, локальный state-файл без внешней блокировки не гарантирует отсутствие дублей. Запускайте один экземпляр.
